# Benchmarks

wise-mode は手順を**増やす**スキル集なので、増やしただけの効果があるかを示せないと
ただ重いだけになる。指標は 1 つに絞る。

## 指標: fix-follow rate

```
fix-follow rate = 直近 N 日以内に触ったファイルを、再び fix 系コミットで触った割合
```

低いほど「一度で正しく直せている」。レビュー指摘数のような自己申告値と違い、
git 履歴だけで測れて後から改竄できない。

```bash
python3 benchmarks/fix_follow_rate.py --since 2026-01-01 --until 2026-04-01 --label before
python3 benchmarks/fix_follow_rate.py --since 2026-04-01 --until 2026-07-01 --label after
```

## A/B の取り方

1. wise-mode を入れる**前**の期間を測る（`--label before`）。
2. 導入後、同じ長さの期間を測る（`--label after`）。
3. 両期間とも **30 コミット以上**。下回ると差はノイズに埋もれる（スクリプトが警告する）。
4. 期間の長さ・チーム人数・リリース頻度を揃える。揃わない比較は捨てる。

## 読み方

- **差が 5 ポイント未満** → 効果なしとみなす。ヒューリスティックの誤差の範囲。
- **after が悪化** → 手順が形骸化しているか、タスクに対して重すぎる。
  `/wise` の Lightweight 判定を見直すか、`/wise-cont` を切る。
- **fix commits は減ったが rework rate が変わらない** → コミットメッセージの
  書き方が変わっただけ。指標ではなく運用を疑う。

## 既知の限界

- コミットメッセージの規約に依存する（`fix:` を使わないチームでは過小に出る）。
- 変更行ではなくファイル単位。大きなファイルほど誤検出しやすい。
- squash merge のリポジトリでは PR 単位の粒度になり、window が実質短くなる。

これらが問題になるほど精度が要るなら、`gh pr list` で PR 単位に紐付け、
`git log -L` で行単位に落とす。それまではこの粒度で十分。
